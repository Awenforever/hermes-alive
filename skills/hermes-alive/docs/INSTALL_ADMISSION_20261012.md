# Real installation admission — 2026-10-12

## Environment and boundary

- Official source snapshot: `f925b01791fe052e7d55dc975750c0bd985aff91`.
- Disposable NAS/Linux Docker; historical image is only the bootstrap carrier.
  Imported Hermes modules were verified under the read-only `/core` snapshot.
- One CPU, 2 GiB memory, 256 PID limit. Networking used the existing NAS proxy.
  Git HTTP/1.1 and a longer uv HTTP timeout were test-container settings only.
- No production data mount, credentials, paired sessions, provider changes,
  gateway launch, live delivery or production restart.
- Complete current Alive shadow-branch source was cloned from a disposable
  local Git fixture using the public `plugins install` command. This is not
  proof of a published GitHub URL installation or an earlier-version upgrade.

## Observed sequence

1. `plugins install <fixture> --force --yes-deps --enable` prepared declared
   dependencies and enabled the package. Security scanning stayed enabled.
2. `alive status` identified the correct profile, succeeded, and reported no
   installed runtime hook and proactive `enabled: false`.
3. The strengthened runner asked Hermes PM for its selected environment and
   used that interpreter for lifecycle operations and encrypted-state probes.
4. Runtime installation succeeded twice. The second installation preserved
   an actual synthetic journal event, consumer checkpoint, identity key,
   content key and decryptable private content, not just an arbitrary file.
5. Same-revision package force refresh followed by runtime installation
   preserved the same evidence. Installed status remained non-proactive.
6. Runtime uninstall removed the hook/source and retained user state.
   Package removal removed the package checkout. Reinstalling the package
   and runtime restored the hook without replacing the retained state.
7. The final probe decrypted the original content and verified event/checkpoint
   identity and unchanged key digests. Runner exited zero with
   `HERMES_ALIVE_INSTALL_ADMISSION_OK`.

The initial simpler real run also passed, but its generic file sentinel alone
did not qualify encrypted state preservation. The subsequent strengthened run
is the evidence for the journal/key/content claims above.

## Complementary local fault evidence

`run_alive_install_admission_contract.py` passed installed-but-unloaded,
malformed status, wrong profile, failed status, unexpectedly proactive status
and installer-timeout cases. None reached runtime installation after refusal.
Timeout output is retained for diagnosis, not interpreted as success.

`run_alive_install_durable_state.py` passed creation and preservation checks;
missing or replaced encryption keys failed validation. A missing key was not
regenerated by the check, and an existing baseline could not be overwritten.
These are synthetic fixture tests, not arbitrary production migration proof.

## What remains unproved

- Installation against the newest upstream commit at eventual release time.
- Real published GitHub source transport and prior-release upgrade, including
  configuration, external authorizations and learned-state migrations.
- Windows native/WSL matrices, complete corruption/recovery and rollback drills.
- Human-calibrated historical usefulness, independent semantic-review quality,
  controlled live canary and stability observation.

Successful dependency admission is necessary, not proof that the new kernel is
ready to replace the legacy production watcher. Keep the goal and those gates
open. Test-only temporary profiles/containers/archives are disposable; no
production state was changed.
