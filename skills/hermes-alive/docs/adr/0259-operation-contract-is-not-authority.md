# ADR 0259 — Describe actual operations without inventing authority

Status: implemented candidate; bounded actual-Core and real-main qualification; fleet and production pending.
Date: 2026-10-27.

## Problem

A real task completed correctly in its retained project, yet the main response
called project instructions an authorization basis and offered an unsupported
workspace-rebinding operation. It also dumped internal identifiers/status keys
into an ordinary answer. Execution guards remained correct. The explanation
failure still matters: users must understand what was done, what can be changed
and what actually authorizes an action.

Do not fix this with a phrase filter, canned response, private persona override
or a separate answering model. The host previously described capabilities across
several long conditional paragraphs. Tool schema and current setup were visible,
but their operation domains and authority were easy to blur.

## One operation registry, current evaluation conditions

The existing validator registry now supplies the schema operation enum and the
current-turn operation catalog. Each entry exposes its accepted fields and whether
the current setup/turn is eligible to have such a request evaluated. It does not
claim the operation is confirmed, valid for a selected item, successful or
currently executing. The existing validators continue to check identity, current
source evidence, exact item/version, source lifetime, scope, confirmation, policy,
Core definitions and execution ownership at the point of use.

The context separates owner/confirmed-scope/Core authorization from project
requirements, interpreted descriptions and historical execution evidence. It
also describes configured work/review/inspection/outcome choices separately from
actual runtime state. An operation catalog is complete for alive_agenda only;
it does not enumerate or disable other Hermes tools. Task revision fields are
not runtime/workspace configuration. Current binding-change operations are empty.
No new operation, approval route, automatic task or transport behavior is added.

This structured contract replaces the repeated pre-LLM intake/management/work
paragraphs. The tool still owns its parameter descriptions and preview/confirmation
requirements. Ordinary answers should follow the Hermes profile's style, explain
actual actions/results directly and keep opaque IDs/internal keys for subsequent
tool calls unless the user needs them. This is communication guidance, not a
forced Alive personality or deterministic outward renderer.

## Verification and limits

The first installed-Core check parses the actual pre-LLM context, compares the
complete operation/field catalog with the real validator and schema, verifies
empty/revoked intake cannot create facts/jobs, then performs an actual project
file task, independent scoped inspection and cold association read. All pass.
Existing owner validation, dispatch, mutation and work-control methods retain
identical AST; only context presentation and its new descriptor change. That is
not proof of natural-language interpretation or a full portable/fleet pass.

Separate actual-Core default/authorized/restarted control cases and a real
inherited-main-model three-turn probe are pending. The latter retains one task
in A, asks from B about supported changes, then asks about the authority and
conditions for later work with reduced history. It must not create jobs/files,
modify the item, enable the runtime or send anything. Review full original
answers after the terminal credential-audit gate; do not score wording by keyword
matching or silently discard an explanation failure.


## Existing grants are not merely evaluation eligibility

The first real-model probe exposed an actual regression before its later queries:
the main model proposed rather than directly recording an explicitly assigned
item, asking the owner to approve it again. The validator correctly rejected an
unrelated evidence_span argument on propose, but a corrected proposal was still
not the requested saved item. The whole run remains failed. No job/file/send was
performed and no operator confirmation was fabricated.

An operation being supported, an existing delegated grant being active, and the
current invocation being eligible are distinct facts. The next candidate reports
the actual verified intake grant alongside a clear-current-assignment mode;
already authorized direct intake does not need per-item renewal. Unclear intent,
missing current evidence, revoked grants and outside-scope actions still require
their existing clarification/confirmation paths. The same source questions are
being requalified, not rewritten to coach the desired answer.

Four actual-Core control groups passed on the initial catalog baseline: guided
setup, three source-free permission configurations, two-process followup recovery
and six autonomous work modes. The corrected candidate also passes actual
serialized active/revoked intake-mode checks plus the empty/revoked no-effect and
project work/independent-inspection/cold case. These controls are not the pending
real-model semantic verdict or an exact whole-suite qualification.


The corrected real three-turn probe now records directly, refuses unsupported
workspace rebinding and preserves the item/job/file/runtime state during queries.
It attributes action authority to the owner rather than project rules. However,
it calls the selected file scope a default and still answers ordinary questions
with a long state dump. Preserve this limited improvement, not a zero-error label.
The descriptor now names the confirmed-setup origin of a selected scope, states
that no unconfigured automatic tools are selected and distinguishes workspace
binding from a filesystem sandbox. These are general capability/provenance facts,
not a default file toolset or a filter for the word “default”. Ordinary answers
should convey the useful result and next condition, while exact handles remain
available for calls and necessary confirmation commands.


## Observation is not execution — 2026-10-28

A further real probe correctly attributed the selected scope but answered an
item-specific question using generic setup information, without reading the item.
It even offered extra read permission although the owner had already requested a
no-change explanation. Brevity must not replace evidence gathering or erase an
item's own waiting condition.

The descriptor now classifies observations, temporary proposals, agenda changes,
Core work submission and Core stop requests separately. An authorized question
that forbids execution/changes still permits the existing owned-record observations;
no new read/execute right or private file access is added. The actual validators
and work guards remain unchanged. Roles must cover exactly the real registry.

Two fresh isolated profiles subsequently exercised opposite retained conditions
through actual inherited-main-model turns: one authorizes later autonomous first
work, the other explicitly waits for a separate owner start. After history
reduction, both queries use actual observations, retain the correct condition and
do not change any item, job, file, runtime activation or delivery state. The normal
case also checks actual work status. Selected file scope is owner-confirmed, not
a universal default; project requirements do not grant action authority.

This is a bounded semantic pass for those two query journeys. Replies remain too
long and occasionally technical; natural sharing, ongoing-work continuation,
independent Git/fleet, migration, lifecycle and production are not accepted by
this result. The earlier failed and partially improved probes remain recorded;
they are not retroactively green. No physical work was repeated for an explanation
check. All real report reads followed termination, credential audit and cleanup.
